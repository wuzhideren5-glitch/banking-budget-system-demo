# 预算读数口径与维度锁定（人工维护，不随 DB 导出覆盖）

> 本节与下方「报告/数据科目树」一并注入分类器提示词。修改后保存即可生效（进程内按文件 mtime 缓存）。

## 1. 「利息收入」与「净利息收入」

- **报告科目较粗层级**：在损益树下常见 **「利息净收入」**（或「净利息收入」）等**汇总**口径，反映息差结果；**不一定**存在名为「利息收入」的独立报告叶子与之一一对应。
- **用户口语「利息收入」**：常指**细分**的利息类收入（如信贷利息、同业利息等）。这类数字在本系统中通常落在 **数据科目（`Axxxx`/`Cxxxx` 等）** 层，且常带 **产品范围**（`product_scope`）。
- **判定规则**：
  - 若用户要的是 **汇总净息类**（含「净利息」「利息净收入」等），可优先用 **报告科目** 较粗节点 + 组织维，**不一定**强制到数据科目。
  - 若用户要的是 **「利息收入」细项**（且未接受净息汇总），**必须**在 `query_spec.data_accounts` 中给出**至少一条非空 `code`**（并尽量带 `name`），或明确引导用户改问净息汇总；**禁止**仅用 L1/L2 报告科目假装已锁定「利息收入」细项。

## 2. 何时必须锁「产品科目」

- 数据科目在清单中常标注 `product_scope=Zxxxx 产品名`。当用户问句涉及**某条线/个金/企金**等且指标落在**非全行共用的产品化科目**上时，应同时锁定 **部门** 和/或 **产品科目**（`products` / `departments`），避免误把全行 SUM 当条线结果。

## 3. `data_query_ready` 的前置条件（与路由提示一致）

- **时间**可执行（`period_description` 或 `year`/`quarter`/`month` 至少一种有效线索）。
- **组织维**：条线语境下 `departments` 与 `products` 不能全空（除非用户明确全行/整体）。
- **指标维**：凡 **损益类细项**（含用户明确说「利息收入」且非净息汇总），**必须**锁到**数据科目代码**或经用户接受改为净息/汇总口径；否则应走 `data_query_incomplete`，`missing_aspects` 含 `metric_scope`。

## 4. 两类「组合」与客户说明方式

本系统读数依赖**成对决策**（不是只写一句自然语言指标名）：

| 组合 | 含义 | 客户需要意会到的点 |
|------|------|-------------------|
| **报告科目 ↔ 数据科目** | 报告树给**展示层级**；真实发生额常在**数据科目**（code 以 A/B/C… 等形式出现） | 若只看报告节点、未落到数据科目，可能只看到汇总或口径与口语「利息收入」等不一致 |
| **部门科目 ↔ 产品科目** | **组织维**与**产品维**共同约束「谁、哪条产品线」 | 条线/个金/企金等口语须变成**部门 code+name** 和/或 **产品 code+name**；否则易与全行汇总混淆 |

**提示用户时的优先顺序**：先说明「要查的是哪条时间线 + 哪个部门/产品 + 报告还是数据科目上的哪个指标」，再谈图表或执行。

**上级优先原则（减少无效追问）**：
- 若已锁定**报告上级科目**并可执行查询，默认其口径已覆盖下级明细，除非用户明确要求“仅某些下级/排除某些下级”，否则不要再追问是否包含下级数据科目。
- 若已锁定**部门上级科目**并可执行查询，默认其口径已覆盖下级产品范围，除非用户明确要求只看某些产品，否则不要再追问下级产品科目。

## 5. 歧义 → 必须走澄清；延续对话要「合并已确认、只问缺口」

- 只要你**不能**在 `query_spec` 里同时写清：**时间** + **（报告/数据科目至少一条可执行锁）** + **（条线语境下部门/产品至少其一或全行声明）**，一律 **route=`data_query_incomplete`**，**不要**猜成 `data_query_ready`。
- 当 **section 三 `pending_query_spec` 非空** 且用户在本轮**补充或修正**了若干维时：`is_continuation=true`，输出中的 `query_spec` 必须是 **pending 与本轮合并后的全文**（已确认维保持 code+name，勿丢）。
- **clarification_message** 建议结构（二段式）：  
  1）**已根据对话可确定的维度**（逐条 code｜name，无则略）；  
  2）**仍需您明确的一项或多项**（用问句或二选一，指向报告/数据或部门/产品中具体缺口）。  
  不要重复追问用户已经说清且已写入 `query_spec` 的维度。

## 6. 相对时间（通用）：最近/近 N 个月、最近/近 N 个季度

- **统一定义（与系统只读 SQL 中 `period_description` 解析一致，勿自行换算法）**  
  对于「最近/近 N 个月」「最近/近 N 个季度」：
  1) 以**自然日“今天”**为锚；  
  2) 从当前所在时间粒度（月/季度）的起点往前回推；  
  3) 取 **N 个已结束的完整周期**（整月或标准季度）计入。  
  - 例：若当前是 **2026 年 4 月任意一天**，`最近3个月` => `M01~M03`（`Y2026`）。  
  - 例：若当前是 **2026 年 4 月任意一天**，`最近6个月/半年` => `Y2025.M10~M12` + `Y2026.M01~M03`。  
  - 例：若当前是 **2026 年 4 月任意一天（Q2）**，`最近一个季度` => `Y2026.Q1`（不是简单“前三个月”字面，而是标准季度）。  
  - 例：若当前是 **2026 年 4 月任意一天（Q2）**，`最近两个季度` => `Y2026.Q1` + `Y2025.Q4`。  
  - 例：若当前是 **2026 年 1 月任意一天**，`最近3个月` 通常跨年到上一年 `M10~M12`。
- **支持表达（时间维已可执行）**  
  - 「最近/近 + 数字 + 个月」：如 `近3个月`、`最近6个月`、`近12个月`；  
  - 「最近/近 + 中文数词 + 个月」：如 `最近三个月`、`近六个月`、`近十二个月`；  
  - 「最近/近半年」：按 `6` 个月处理。  
  - 「最近/近 + 数字 + 个季度」：如 `最近1个季度`、`近2个季度`；  
  - 「最近/近 + 中文数词 + 个季度」：如 `最近一个季度`、`近两个季度`、`近三季度`；  
  - 未显式数字但表达为「最近季度/近一季度」时，按 `1` 个季度处理。  
- **分类器行为（重要）**  
  - 命中上述表达时，**时间维度已可执行**：在 `query_spec.period_description` 填用户原话即可；`year`/`quarter`/`month` 可留空，由系统查询层解析。  
  - **禁止**将这类输入判为 `missing_aspects: ["time"]`，**禁止**追问「请给起止月」。  
  - 仅当用户明确提出**不同口径**（例如要“含当月未完月”“按自然日滚动”“季度按非标准季度划分”）时，才进入时间澄清。

## 6.1 比较口径默认值（未确认时）

- 比较维（预算/实际、同比、环比）为**可选项**，不是阻塞条件。
- 用户未明确要求比较时，默认 **`comparison_type = none`**（不做比较拆分分析），直接按单口径汇总输出。
- 仅当用户明确提到「预算vs实际 / 差异 / 同比 / 环比 / 对比 / 比较」时，再启用比较口径。

## 7. 回复中须写明的「锁定清单」（与 user 模板一致）

当 `route=data_query_ready` 时，**answer_body 开头**必须用分点列出（有则写 code｜name，无则写「未锁定」及原因）：

- 报告科目
- 数据科目
- 部门科目
- 产品科目
- 时间范围（可与 `period_description` 一致）

（便于客户与下游规划步骤对齐，避免只有自然语言描述没有代码。）
