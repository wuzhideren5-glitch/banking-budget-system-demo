## 范围与演进（交付范围与多用户升级）

本节约定与 **System PDD §2.4**、**Database PDD** / **ERD** 表头 **「交付范围」** 共用同一阶段划分，实现与评审时不得与下文冲突。

### 当前目标版本（内网多用户）

- **部署与身份**：后端部署于内网服务器，用户经浏览器访问；实现多用户登录、会话隔离与 RBAC。
- **界面（Figma）**：保留 **「用户和权限管理」**、**「系统设定控制」** 等入口，并在该信息架构内落地真实管理能力。
- **审计**：`operation_log.user_id`、`ip_address` 必须绑定真实登录用户与访问来源，满足 **E.2** 可追溯要求。

### 后续版本（增强演进）

- 在同一架构上扩展审批流、任务调度、更细粒度权限模型等增强能力。
- 若引入新权限域或新分析底层库结构，须同步修订本节、**System PDD §2.4** 与 Database/ERD 说明，保证四文档一致。

---

**实体名与物理表名**：本规则中出现的 **PascalCase**（如 `BudgetData`、`BudgetSummary`、`OperationLog`、`DataAccount`）指**逻辑实体**，与数据模型 / ORM 类名方向一致。**SQLite 实际表名**必须为 **snake_case**，且与数据库 PDD 开篇**「命名约定（文档实体名与 SQLite 物理表名）」**中的对照表**逐字一致**；编写迁移、手写 SQL、ORM 映射（如 `__tablename__`）时以该表为唯一权威，禁止按类名默认推导表名或自行改写拼写。

## 开发与架构原则（Engineering Principles）

本章节约定实现、联调与代码评审时的**底线要求**。若与 **System PDD** 中功能或体验描述冲突且涉及工程/安全/数据口径，**以本章节为准**，并应回溯修订 System PDD 或实现。

**条款分级**：**必须（MUST）**、**应当（SHOULD）**、**禁止（MUST NOT）**。

### E.1 财务正确性与口径


| 级别     | 要求                                                                                                                                      |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| MUST   | **单一事实来源**：业务金额以 `BudgetData`（行由 `data_acct_code`、`product_code`、`period_id`、`version_id`、`budget_actual` 等与数据库 PDD 联合唯一约束一致）与字典（`DataAccount` 等）为唯一权威来源；汇总展示以计算引擎产出及 `BudgetSummary` 为准。禁止前端、报表脚本或 Agent 以「自行求和」替代引擎结果作为持久化或对外结论依据。 |
| MUST   | **精度与舍入**：存储精度严格符合各科目 **`DataAccount.value_type`**（数值类型：金额/百分比/户数等）；**存储小数位**以 **System PDD §2.2.1**「value_type 与存储小数位」表为产品锚点，并须在代码或配置处可查证（未列出的 `value_type` 须在实现中定义小数位并回填文档）。舍入与换算仅在服务端统一实现。同一数据科目在相同 **`budget_actual`**（预算/实际口径）下，**不得**混用不同舍入/换算策略。UI 展示精度**不得**反向污染存储值。                               |
| MUST   | **公式与手工互斥**：存在有效预算/实际公式的数据科目，在每一 **`budget_actual`** 粒度下对应的 `BudgetData` 单元格禁止持久化手工录入值；字典或公式变更后必须通过 `need_calc` 与重算路径刷新依赖链，覆盖受影响的 **`budget_actual`** 取值。**依赖标脏须级联**：在同一 `version_id` 下，凡被标需重算的行，其公式依赖链上的**所有下游** `BudgetData` 行**必须**一并标为需重算，直至重算完成（详见 **System PDD §2.2**「need_calc 与重算」）。                                                      |
| MUST   | **版本、期间与数据口径**：`data_acct_code`、`product_code`、`period_id`、`version_id` 与 **`budget_actual`**（**`1`** = 实际口径，**`0`** = 预算口径，见数据库 PDD `BudgetData`）组成的业务唯一性，须在 API 与持久化层与 `budget_data` 联合唯一约束一致地双重校验，禁止静默覆盖。                                      |
| MUST   | **`current_month` 月份窗口强约束**：对任一版本 `X=current_month`，`BudgetData` 必须满足 `X` 月前仅实际（`budget_actual=1`）、`X` 月及后仅预算（`budget_actual=0`）；`X=1` 时仅预算，`X=13` 时仅实际。版本继承、导入、录入加载等路径发现违规记录时，必须删除违规口径行，不得仅置零保留脏行。 |
| MUST   | **版本继承迁移口径**：创建新版本并继承父版本时，只允许迁移符合新版本 `current_month` 的预算/实际记录（如 `X=5`：迁 `1..4` 月实际 + `5..12` 月预算；`X=1` 仅预算；`X=13` 仅实际）；禁止将父版本全量口径复制后依赖前端过滤。 |
| SHOULD | 关键计算路径（公式解析、滚动预算拼接、预聚合）具备可重复执行的自动化校验或与抽样 Excel 对账用例。                                                                                    |

**与 Figma 控件的字段对应（工程备忘）**：**`DataAccount.value_type`** 与「数据科目维护」界面**数值类型**列对应；**`BudgetData.budget_actual`** 与「预算基础数据维护」界面**预算值 / 实际值**切换对应；**`need_calc`** 仅为引擎标脏，**无**对应界面控件（详见 **System PDD §4.8**、**§2.2**）。

### E.2 可追溯与可审计


| 级别     | 要求                                                                                                                    |
| ------ | --------------------------------------------------------------------------------------------------------------------- |
| MUST   | **凡改必记**：凡导致 `BudgetData`、**字典表**（如 `DataAccount`、`ReportAccount`、`DeptAccount`、`ProductType`、`Period`、`ChartTemplate` 等）、**字典映射表**（如 `ReportDataMapping`、`DeptProductMapping`）、**版本**等核心数据变更的路径（人工、批量导入、Agent），**必须**写入 `OperationLog`，并保留可追溯的前后快照（JSON 等），字段语义与 System PDD / 实现约定一致。 |
| SHOULD | 报表、导出与 Agent 结论文本能够还原到：**科目代码/名称、版本、期间、`budget_actual`**，满足内控与事后解释需要。                                                     |
| SHOULD | 变更日志应携带登录用户、角色、会话上下文、业务年度、版本与目标库信息；其中 **`target_table` 填写 SQLite 物理表名（snake_case）**，与数据库 PDD「命名约定」对照表一致。                                                        |


### E.3 安全与 AI 治理


| 级别       | 要求                                                                                                        |
| -------- | --------------------------------------------------------------------------------------------------------- |
| MUST NOT | API Key、密钥及等价凭据**不得**进入前端 bundle、仓库或日志明文。若使用 `.env` 等本地文件承载密钥，**必须**将对应文件或路径模式列入 `.gitignore`，禁止提交版本库。                            |
| MUST     | **高危写库人机共决**：批量修改、跨版本写入等，**必须**向用户展示：自然语言行动计划、影响行数、将执行的 SQL（或等价可审计语句），并经显式确认后方可执行（参见 **System PDD §2.3**）。 |
| MUST NOT | Agent **不得**在未走受控工具链与确认流的情况下执行任意写库 SQL。                                                                   |
| SHOULD   | 分析类能力默认只读；写库类能力仅通过固定、可测试的后端接口暴露。                                                                          |


### E.4 性能与一致性


| 级别     | 要求                                                                                                        |
| ------ | --------------------------------------------------------------------------------------------------------- |
| MUST   | **大面查询走预聚合**：当前年度多版本透视读取 `budget_summary`；多年度对比透视读取 `compare.db.compare_budget_summary`（或文档定义的等价预聚合结果）。**禁止**为交互查询对全量 `budget_data` 做实时全表聚合。 |
| SHOULD | 批量导入、全版本重算等长任务具备超时、进度或后台任务策略，避免长时间独占数据库连接。                                                                |
| SHOULD | 异步轮询重算与用户触发的「立即计算」的优先级与完成后界面与库内数据一致，并在 System PDD / 运维说明中可查证。                                                     |


### E.5 工程与交付


| 级别     | 要求                                                          |
| ------ | ----------------------------------------------------------- |
| SHOULD | 前后端对**期间、版本、`budget_actual`、产品由字典推导、`DataAccount.value_type`** 等契约使用 OpenAPI/共享类型，避免口径漂移。 |
| MUST   | **导入幂等**：批量导入同一文件的重复执行行为（拒绝 / 跳过 / 覆盖）**必须**在文档与实现中明确且一致。   |
| MUST   | **预算输入导入闭环**：预算基础数据导入必须提供「下载模板、上传预览、导入并下载结果文件」三步闭环；结果文件须在用户上传文件基础上回写导入评估（颜色与失败原因），不得只在页面临时展示后丢失。 |
| SHOULD | 纯本地、无 CDN 的构建与依赖策略（参见技术栈章节）在升级依赖时回归验证，避免引入破坏离线安装的加载方式。      |


### E.6 用户体验与防错


| 级别   | 要求                                                                                     |
| ---- | -------------------------------------------------------------------------------------- |
| MUST | 高密度录入区保持 **Tab/方向键**导航与只读/可编辑单元格的**视觉区分**。                                             |
| MUST | **数据库强约束前端同步**：凡 Database PDD 定义为 `PK` / `NOT NULL` 的输入字段（如 `DataAccount.data_acct_code`、`data_acct_name`，`ProductType.product_code`、`product_name` 等），前端在提交前**必须**执行必填与格式校验；不得允许空主键、空必填字段进入保存流程。 |
| MUST | **预算输入重算体验约束**：预算输入页面禁止在每次单元格保存后立即触发全局或级联重算；重算触发应收敛为页面首次进入、页面离开、用户显式点击「全局计算并刷新」等有限事件，避免频繁跳动与卡顿。 |
| MUST | **数据科目公式产品边界**：同一产品内公式计算只允许读取该产品下的 `budget_data` 数值；**适用所有产品科目**（`applies_to_all_products=1`）在重算时必须按产品逐一遍历执行同一公式（对每个产品独立取值并回写），禁止跨产品引用或广播拷贝值。 |
| MUST | **适用所有产品公式引用约束**：当目标数据科目为“适用所有产品科目”时，其预算式/实际式仅可引用同为“适用所有产品科目”的数据科目；前端公式树必须对不满足约束的科目灰显且禁用，后端保存接口必须执行同等强校验并拒绝越界引用。 |
| MUST | **编辑入口一致且可恢复焦点**：表格“编辑”按钮、单元格点击、键盘导航三种入口必须收敛到同一编辑状态机；当“编辑”按钮被点击时，焦点**必须**回到该行首个关键字段（通常为代码主键列），不得出现“按钮可点但字段不可编辑”。 |
| MUST | **保存并刷新不得静默丢数据**：存在新增但未落库的行时，点击“保存并刷新”必须先执行写库（或明确阻止并提示原因）；禁止刷新后静默丢弃用户已输入内容。 |
| MUST | **保存并刷新后需明确反馈数据来源**：执行“保存并刷新”后，前端必须明确提示“已从数据库刷新”（或等价文案），让用户确认当前展示为后端最新结果；该交互作为基础维护页统一设计惯例。 |
| MUST | **主键冲突回焦主键字段**：当新增/编辑因 `PK` 冲突（如“代码已存在”）或主键格式错误而失败时，前端必须立即提示“格式要求 + 正确示例”，并将焦点强制返回该记录的主键输入框；禁止将焦点停留在非主键字段导致用户无法继续修正。 |
| MUST | **基础维护页只允许数据库真数据源**：数据科目、报告科目、产品科目、部门科目四个基础维护界面，列表/树/映射展示**必须**来自后端接口对 `common.db` 对应表的查询结果；当底层表为空时界面必须为空状态，**禁止**展示硬编码示例数据。 |
| MUST | **CRUD 写后读一致性**：上述四个界面的新增、编辑、删除、映射操作必须先写库成功再更新前端状态；刷新后结果必须与数据库再次查询一致，禁止“前端改了但库没变”或“库已变但界面不一致”。 |
| MUST | **Agent 规划确认文案去重**：同一条确认消息中，不得同时在正文和透视建议卡片重复展示同一透视解释文本。 |
| MUST | **Agent 锁定维度块紧凑展示**：`已锁定的查询维度`区块应按固定维度顺序紧凑输出，禁止插入无业务意义空行。 |
| MUST | **对比透视搜索预填保持**：多年度对比透视在应用 Agent 建议后，搜索框必须保留 `pivot_search_text`（报告/数据科目 code）以支持快速过滤。 |
| MUST | **部门-产品映射唯一归属**：`DeptProductMapping` 必须满足“部门叶子节点一对多产品、单产品全局唯一归属”规则；同一 `product_code` 不得映射到多个 `dept_code`，且仅允许叶子部门节点创建映射。 |
| MUST NOT | **禁止修改存在下级的树节点编码**：对树形主数据（至少包括 `ReportAccount`、`DeptAccount`），若节点已存在下级节点，则其主键编码**不得**被编辑或重命名；前端必须阻止提交并提示原因，避免层级路径、映射关系与历史引用失配。 |
| MUST NOT | **禁止用前端临时状态冒充持久化成功**：未提交到后端并落库的数据，必须标记为未保存并在刷新前阻断或告警；不得以 toast/提示文案替代实际写库。 |
| SHOULD | 对新增行采用“占位提示 + 最小可点击区”设计（空值字段仍可明显点击编辑），避免因空内容导致点击区域过小或焦点丢失。 |
| MUST | 破坏性操作（删除字典项、解除映射、删除版本等）**必须**依赖检查与用户确认；删除 `DataAccount` 记录前**必须**校验公式引用（参见 **System PDD §2.2**）。 |
| MUST | **Excel 导出血缘**：导出中的公式与分组（Group & Outline）**必须**与在线计算逻辑一致；**在线结果与导出公式结果不一致视为 P0 缺陷**。   |


### E.7 前端实现与 Figma 一致性（UI Fidelity）

产品已在 Figma 中完成界面设计，并以工作区 **`src_from_Figma/`**（自 Figma 导出的参考实现：组件结构、样式与资源）作为**视觉与交互的权威基线**。该目录作为**只读参照**：AI 辅助编码、自动化工具与人工开发**不得**直接改写其中文件；须将所需内容**复制**到仓库根目录下的 **`src/`**（与 `src_from_Figma/` **平级**）后再行开发与联调，以便长期保持导出物与 Figma 定稿可追溯、可对比。若确需变更可交付前端根路径，须同步修订本节与 README / System PDD。

| 级别       | 要求                                                                                                                                                                                                                                                                 |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| MUST NOT | **`src_from_Figma/` 禁止就地修改**：**不得**在 `src_from_Figma/` 内编辑、删除、移动或重命名文件，**不得**仅在该目录下挂载路由或提交业务功能改动；合并请求中若出现对该目录的修改，视为违反本规则（除非为**自 Figma 重新导出**后的整包替换，且由产品明确发起）。                                                                                                                                 |
